# 정제 입력 토큰 상세 조사

- 일자: 2026-11-16 (Asia/Seoul)
- 범위: 실제 사용량 로그와 설치본/현재 소스, 전사문을 이용한 로컬 요청 재구성. 제품 코드 변경 없음.

## 실제 응답

최근 성공 응답 3건은 각각 입력 4,233 / 3,815 / 3,967토큰으로 합계 12,015이다.
출력은 1,093 / 1,023 / 1,297토큰, 합계 3,413이다. 12.3k라는 사용자 화면 값과
완전히 동일한 집계인지는 확인되지 않았다. 로컬 로그에서 요청당 12.3k인 성공 응답은 없다.
로그에는 실패 요청, 이전 프로세스 내부 사용량, 작업/session 식별자가 없다.

본문 3,935 / 3,987 / 3,986자, 문맥 4,018 / 3,410 / 3,397자,
system 1,739자라는 로그 값과 모두 일치하는 원문을 찾아 요청을 재구성했다.
실측 토큰의 구성 항목별 분리는 기록돼 있지 않아 문자 수로 나누었다.

## 해당 전사문 전체의 요청 구성

원문은 19,525자이며 경계의 공백 4자를 제외한 본문 19,521자가 5개 요청으로 전송된다.

| 항목 | 총 문자 수 | 입력 문자 비중 |
|---|---:|---:|
| 본문 | 19,521 | 42.79% |
| ASR 및 앞뒤 문맥, 프롬프트 포장 | 17,401 | 38.15% |
| system instruction (1,739 × 5) | 8,695 | 19.06% |
| 합계 | 45,617 | 100% |

ASR 배열은 요청마다 80행, 총 400행이다. 배열 값만 11,938자다.
각 행은 시작/끝 문자 위치, 시작 초, avg_logprob, no_speech_prob를 포함한다.
본문 앞뒤는 최대 각 240자이고 별도 설명과 field 이름도 매 요청 반복된다.
첫 요청에는 대체 ASR 후보 JSON 1,030자가 있으며 나머지는 빈 후보 JSON 22자다.
용어집은 비어 있다. 이 정제 요청에 PDF 전체나 노트 템플릿은 들어가지 않는다.

avg_logprob < -1.1 또는 no_speech_prob > 0.7인 행만 세면 32 / 0 / 0 / 0 / 0행이다.
이는 해당 두 지표에 따른 선별 후보이지, 제외한 행이 정확하다는 보장은 아니다.

## 절감 후보를 실제 입력으로 재구성한 결과

| 조건 | 전체 입력 문자 | 현행 대비 감소 |
|---|---:|---:|
| 현행 | 45,617 | — |
| 위 두 지표의 의심 행만 포함 | 34,592 | 24.17% |
| 의심 행 선별 + 525자 system 후보 | 28,522 | 37.48% |
| ASR 행 전부 제외 + 짧은 system | 26,584 | 41.72% |

마지막 방식은 timestamp/confidence 근거를 잃는 데 비해 추가 절감이 작아 우선하지 않는다.
첫 두 방식도 실제 모델의 정제 품질은 A/B 검증하지 않았다. 이 비율은 문자 비율이며
토큰/요금 절감률로 해석하면 안 된다. 수치만 있는 JSON은 문자 비중과 토큰 비중이 다를 수 있다.

## 반복과 다른 단계

- 현재 정제는 모든 chunk가 완료돼야 결과를 저장한다. 뒤 구간 실패 후 수동 재실행하면
  성공했던 앞 구간도 다시 요청한다. 동일 입력 기준 앞 세 요청만 재처리해도
  실측 12,015 입력 토큰 규모가 반복될 수 있다. 성공 구간의 체크포인트와 입력/설정
  지문 검증을 통한 재사용이 우선적인 낭비 방지 방법이다.
- 설치본에는 SDK retry_options가 없다. 따라서 지금 관찰한 사용량을 새로 추가한
  2회 재시도 정책 탓으로 설명할 수 없다. 소스의 재시도 수정은 설치본과 다르다.
- high thinking 설정은 확인했지만, 이것을 입력 토큰 증가의 원인으로 단정하지 않는다.
  thinking은 출력 측 비용/지연과 별도로 확인해야 하고 현재 로그에는 thinking 토큰이 없다.
- 실제 성공 로그는 refine뿐이다. 노트 생성은 별도 작업이며 chunk 노트 생성 후 그 결과를
  병합 요청 입력으로 다시 사용한다. PDF가 있으면 최초 참고문 추출과 참고문의 반복 입력도
  생기지만 이번 세 정제 요청의 구성에는 해당하지 않는다.
- 미리보기 재요청은 매번 생성하며, 변경 없는 미리보기 결과의 저장만 재사용한다.

## 권장 순서

1. 성공 구간 재사용으로 실패 후 재실행 낭비를 막는다. 입력/설정/자료 변경 시 무효화한다.
2. ASR은 의심 구간과 실제 대체 후보만 전송하고 정상 구간의 timestamp는 필요한 최소 위치 정보로 유지한다.
3. system instruction을 짧게 만들되 의미/숫자/고유명사 보존과 불확실성 규칙을 유지하고 A/B 검증한다.
4. 더 큰 chunk로 호출 수와 system/문맥 반복을 줄이는 실험은 출력 잘림과 누락을 검증한 뒤 적용한다.

## 정확도 및 계수 한계

실측 응답 토큰 수는 확인했으나 항목별 정확한 토큰 기여도는 현재 로그만으로 계산할 수 없다.
모델마다 tokenizer가 다르므로 다른 모델의 tokenizer나 문자 비율을 토큰 수로 제시하지 않았다.
CountTokens를 통한 계수를 준비했으나 이 실행 환경의 SecretStore에서 API key를 받지 못해
계수 요청 자체는 보내지 못했다. 앱이 가진 인증으로 모델별 CountTokens에 원래 요청과
항목을 제거한 요청들을 넣어 차이를 측정해야 하며, 단독 계수의 단순 합은 경계 토큰 때문에
완전히 일치하지 않을 수 있다. 키를 파일이나 대화에 복사하지 않는다.
추론 API 호출, 모델·설정 변경, 앱 재빌드·설치는 하지 않았다.
